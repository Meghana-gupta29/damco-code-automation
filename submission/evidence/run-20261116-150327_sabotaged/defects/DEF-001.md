# DEF-001: Item list endpoint returns every user's items to non-superusers (data leak)

- **Severity:** Sev1
- **Status:** Fixed (pending verification)
- **Classification (AI):** product_bug (confidence: high)
- **AI recommendation:** fix_code
- **Failing tests:** TC-017, TC-043
- **Suspect module:** `backend/app/api/routes/items.py` read_items(), non-superuser else-branch: the `.where(Item.owner_id == current_user.id)` filter was removed from both the count statement and the item select statement
- **Regression since app commit:** aabb901
- **Run:** run-20261116-150327

## Root cause (AI)
The diff deleted the owner_id filter in the non-superuser branch of GET /items/. That branch is now identical to the superuser branch, so any authenticated user gets all users' items and a global count.

## Why this classification
Both failures trace directly to the changed lines. TC-017 shows extra item IDs belonging to other users. TC-043 shows user B not getting the empty state because A's item is returned. Nothing suggests this is a deliberate rule change, since the page copy says 'Create and manage your items' and the single-item endpoints still enforce ownership with 403. This is a cross-tenant data exposure. The frontend is not at fault because it correctly renders whatever the API returns.

## Steps to reproduce
1. Create user A and user B (non-superusers)
2. As A, POST /api/v1/items/ twice; as B, POST once
3. As A, GET /api/v1/items/
4. Alternatively, in the UI log in as B, who has no items, and open /items

## Expected
A receives 200 with only A's 2 items and count=2. B sees the empty state 'You don't have any items yet'.

## Actual
The response includes items owned by other users, and count covers all items in the table. B sees A's items instead of the empty state.
